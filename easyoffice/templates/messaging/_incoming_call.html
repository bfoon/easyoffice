{% comment %} templates/messaging/_incoming_call.html ======================================= 📞 The global incoming-call handler. WHAT WAS WRONG -------------- base.html carried the banner's CSS, the banner markup, and two buttons wired to eoCallBannerAccept() / eoCallBannerDecline() — and a comment saying "Polls /messages/call/incoming/ on every page". Neither the poller nor either function existed anywhere in the project. chat_room.html even had a note deferring to it ("base.html's global incoming-call banner polls /call/incoming/"), so both sides assumed the other did the work. The result was a call that looked fine from the caller's seat: the ring POST succeeded, the server stashed the ring record, the offer and ICE candidates went out — and nobody ever asked the server whether there was a call waiting. The banner was a display:none div that nothing could show. The caller sat on "Calling…" until the 40-second timeout. So this is the missing half. Include it ONCE from base.html, replacing the comment block, inside the same guard that hides it on the popup: {% if request.user.is_authenticated and request.resolver_match.url_name != 'call_window' %} {% include "messaging/_incoming_call.html" %} {% endif %} The banner markup already in base.html can stay exactly as it is — this file finds it by id and drives it. If it isn't on the page, this builds its own, so the include also works standalone. WHY POLLING AND NOT A SOCKET ---------------------------- A ring must reach you on the leave-request page, the task list, anywhere. The chat WebSocket only exists on chat pages, so it cannot be the delivery mechanism for a call — it can only make one faster. The poll is what guarantees arrival; the socket path is an optimisation that fires when a chat page happens to be open. Three seconds is the cadence, against a 35-second server-side ring TTL: fast enough that the callee's phone rings while the caller still expects it to, slow enough to be one cheap cache read per user per three seconds. {% endcomment %}
